
# Process-Level Fault Injection

## Overview

Process-level fault injection tests the behaviour of the QEMU process when it is forcibly terminated at specific points during a CXL firmware transfer.

The tests run against a QEMU-emulated CXL Type 3 device. A host-side Python controller coordinates the firmware transfer, waits for a predefined checkpoint, terminates QEMU using `SIGKILL`, restarts the VM, and verifies that the guest becomes accessible again.

The purpose is to validate QEMU process termination and recovery, not firmware-update recovery.

## Architecture

Process-level fault injection involves two environments:

| Component | Environment | Responsibility |
|---|---|---|
| QEMU process | Arch Linux host | Runs the virtual machine |
| Fault controller | Arch Linux host | Coordinates fault injection and records results |
| CXL firmware client | Ubuntu guest | Performs the firmware transfer and reports checkpoints |
| CXL Type 3 device | QEMU guest | Device under test |

The controller communicates with the guest through SSH and receives checkpoint notifications from the client through a TCP connection.

**Important:** Process-level fault-injection logs are generated by the controller on the Arch host. They are not stored by the Ubuntu guest client.

## Fault Scenarios

The following checkpoints are supported:

| ID | Checkpoint | Description |
|---|---|---|
| PF1 | Before INITIATE | Terminate QEMU before the firmware transfer begins |
| PF2 | After INITIATE | Terminate QEMU after INITIATE completes, before the first CONTINUE |
| PF3-1 | After CONTINUE 1 | Terminate QEMU after the first CONTINUE completes |
| PF3-2 | After CONTINUE 2 | Terminate QEMU after the second CONTINUE completes |
| PF4 | Before END | Terminate QEMU after the final CONTINUE completes, before END |

Firmware activation is outside the scope of these tests.

## Requirements

### Arch Linux host

- QEMU built with CXL support.
- Python 3.
- QEMU process-fault controller.
- SSH access to the Ubuntu guest.
- QEMU overlay disk and base VM image.
- The repository cloned on the Arch host.

### Ubuntu guest

- Linux kernel with CXL raw mailbox command support.
- QEMU-emulated CXL Type 3 device available at `/dev/cxl/mem0`.
- Built firmware-management client.
- Synthetic firmware image at `firmware/synthetic-test-8k.bin`.
- SSH server enabled.

## Execution

The controller must be executed on the **Arch Linux host**. The firmware client executes inside the **Ubuntu guest**.

Run one scenario at a time. Do not launch another QEMU process while the controller is managing the VM.

From the repository clone on the Arch host:

```bash
python3 tools/host/cxl_process_fault_controller.py --checkpoint PF1

python3 tools/host/cxl_process_fault_controller.py --checkpoint PF2

python3 tools/host/cxl_process_fault_controller.py --checkpoint PF3 --continue-index 1

python3 tools/host/cxl_process_fault_controller.py --checkpoint PF3 --continue-index 2

python3 tools/host/cxl_process_fault_controller.py --checkpoint PF4
```

### Execution procedure

1. The controller starts QEMU using the overlay disk.
2. The controller waits for the Ubuntu guest to boot and become accessible over SSH.
3. The controller waits for the guest's CXL device to become available.
4. The controller launches the firmware client through SSH.
5. The user selects the required kernel in GRUB, if prompted.
6. The user enters the sudo password, if prompted.
7. The client waits for the user to enter `TRANSFER`.
8. The client performs the transfer and reports the configured checkpoint.
9. The controller receives the checkpoint notification.
10. The controller terminates QEMU using `SIGKILL`.
11. The controller restarts QEMU.
12. The controller verifies SSH connectivity and the presence of `/dev/cxl/mem0`.
13. The controller records the test result.

The controller manages QEMU until the test finishes. Use `Ctrl+C` in the controller terminal when you want to stop the restarted QEMU instance.

## Logging

Process-level logs are generated and maintained on the **Arch Linux host**, not by the Ubuntu guest client.

The intended project log location is:

```text
logs/process-fault/
├── <test-id>.jsonl
└── qemu-<test-id>.log
```

### JSONL controller logs

The JSONL logs record:

- Test identifier and selected checkpoint.
- Checkpoint notification and associated transfer details.
- QEMU process ID.
- QEMU termination using `SIGKILL`.
- QEMU restart.
- SSH availability and authentication.
- CXL device availability at `/dev/cxl/mem0`.
- Test completion and cleanup events.

### QEMU output logs

The separate QEMU output log records the emulator's standard output and standard error for that test run.

### Log location

The controller must be configured to write to:

```text
logs/process-fault/
```

This directory is relative to the repository clone on the Arch host. The Ubuntu guest's repository clone is separate and does not automatically receive these logs.

## Pass/Fail Criteria

A process-level fault-injection test passes when all the following conditions are satisfied:

1. The expected checkpoint is received.
2. QEMU is terminated using `SIGKILL`.
3. QEMU restarts successfully.
4. SSH connectivity to the Ubuntu guest is restored.
5. `/dev/cxl/mem0` becomes available again.
6. The controller records the test result.

The test fails if any required condition is not satisfied.

## Scope and Limitations

These tests validate QEMU process termination and VM recovery at selected firmware-transfer checkpoints.

They do not validate:

- Firmware-transfer recovery after QEMU restarts.
- Persistence of firmware-transfer state.
- Firmware activation.
- Firmware correctness or bootability.
- Recovery of an interrupted firmware update.

The CXL device uses a volatile RAM backend. CCI firmware-transfer state resets when QEMU restarts. These tests therefore establish process and VM recovery, not firmware-update recovery.

## Safety Notes

- The controller uses `SIGKILL`, which forcibly terminates QEMU.
- The controller uses an overlay disk to avoid modifying the base VM disk.
- Do not run multiple controller instances simultaneously.
- Do not launch a separate QEMU instance while the controller is managing the VM.
- Keep the base VM disk untouched.
